三、玩家手牌状态（4 种）与决策动作（3 种）

手牌张数

0 张⟶ 2 张(起手)⟶ 3 张(补/强制)

你说的「默认发三张」= 每人最终 3 张 ✓（2 张起手 + 补 1 张达成）；「补不补由我自己」= 没有单鬼时补不补由玩家点按钮决定 ✓——两条都成立，规则不用改。

决策子状态（我回合 15s 内）

等待⟶ 已举手(示意)⟶ 已过 / 已补

举手 = 未轮到时提前示意要补（全桌可见 ✋，可撤销）；轮到我时若已举手 → 自动补牌不用再点。大牌（天公9/8 等）自动亮牌全桌可见。

六、你问的三个设计点

① 底注是房间级配置，不是每轮重选
建房时房主从预设档位选一个（50 / 100 / 200 / 1000），整场固定。每局开始不再弹下注面板——参加确认时自动按房间底注扣。
② 每局结束后：参加/不参加倒计时，默认参加
结算面板点「下一局」→ 8 秒倒计时，期间可点「本局不参加」（该局旁观，看得见公共信息但不下注不比牌）；不点 = 自动继续。下一局开始前可再改主意参加。
③ 纯前端 → 需要服务端 + 机器人
当前 musaiyu.pages.dev 是纯前端单机版：洗牌/发牌/比较全在浏览器里，AI 是本地模拟，刷新即丢局。要多人联机必须加服务端权威（洗牌/发牌/比较/结算全在服务端，客户端只显示+发操作），机器人也在服务端跑——具体两条路线见下节。

七、部署架构（两条路线）

路线 A · Node + socket.io（部署 shanbox）

  • 服务端：Node + Express + socket.io，supervisord 托管（与 yxx 同机不同端口）
  • 机器人：服务端 bot 模块，同一套决策接口
  • 优点：与 SPEC 第 6 节一致；国内直连快（shanbox 域名）
  • 缺点：需要自己运维

路线 B · Cloudflare Workers + Durable Objects

  • 前端已在 musaiyu.pages.dev，WS 走同域最顺
  • 优点：免运维、全球低延迟、与前端同账号
  • 缺点：DO 有免费额度；国内访问 pages.dev 稳定性一般

机器人：服务端 bot 模块（读牌型 → 简单策略：好牌补/差牌过 + 随机扰动），走与真人相同的决策接口，服务端不区分。
